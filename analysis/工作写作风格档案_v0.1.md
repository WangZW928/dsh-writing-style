# 工作写作风格档案 v0.1

_基于三篇工作文章的首轮观察 · 2026-11-05 · 用于后续起草与润色，不涉及模型训练或插件开发_

---

## 📋 画像摘要与适用范围

你的这组文章呈现出一种**工程实践驱动的解释型技术写作**：面向有一定技术基础的同事，从当前工作或学习需要出发，把问题分层、把相近概念放在一起比较，再借助具体材料解释原因，最后讨论对实际工作的影响。

辨识度较高的不是某个口头禅，而是三种组合：

- **技术说明＋个人判断**：既解释对象，也交代“我目前关注什么”“对我们的工作有什么价值”。
- **对比拆解＋机制解释**：不满足于列出差异，还要说明差异为何影响实现、效率或使用方式。
- **明确结论＋适用条件**：有立场时直接表达，涉及推断、转述和未验证内容时又交代范围。

这不是纯论文体，也不是产品宣传或会议流水账。更接近“把自己在工作中理解清楚的事情，带着判断讲给同事听”。“讲清楚”优先于“写得漂亮”。

## 🔍 跨文章反复出现的写作习惯

### 1. 先说明这件事为什么与工作有关

三篇开头都没有先铺很长的行业背景，而是先建立写作目的：当前使用方式、公司相关工作，或学习某个技术环节能带来什么帮助。

- A：“本文主要对我当下工作模式（内网AMReX开发）中，如何使用AI，进行一些思考和总结。”[A：5](<../corpus/derived/AMReX开发中的AI助力总结.md#L5>)
- B：“与公司当前 Agent 转码及性能优化 工作直接相关的内容主要集中在三个方向：”[B：7](<../corpus/derived/KubeCon China 2026 参会技术报告.md#L7>)
- C：“学习编译流程，查看汇编代码，有助于为开发任务提供优化思路。”[C：5](<../corpus/derived/异构编程的编译流程（笔记）.md#L5>)

**复用规则：**开头先回答“为什么现在写这个、解决什么理解或工作问题”，再进入对象介绍。少用与任务联系较弱的宏大开场。

### 2. 习惯先拆对象，再讨论能力与限制

你倾向于把一个大问题拆成能逐项讨论的部分，而不是把概念混在同一段里。

- A 将工作基础分为“AMReX框架，SCALE编程，计算芯片架构”，再讨论各部分的 AI 助力。[A：9–27](<../corpus/derived/AMReX开发中的AI助力总结.md#L9-L27>)
- B 提出语义层、能力层、实现层，分别回答原代码目标、平台能力和实现方式。[B：33–39](<../corpus/derived/KubeCon China 2026 参会技术报告.md#L33-L39>)
- C 按编译环节和中间产物展开，把整体流程拆成可查看的阶段。[C：9–43](<../corpus/derived/异构编程的编译流程（笔记）.md#L9-L43>)

**复用规则：**分类要服务于后续解释或决策。无需为了整齐，固定写成三点；对象真实存在几层，就分几层。

### 3. 用对比建立理解，而不只做名词解释

比较是这组文章里较稳定的解释工具：Chat 与 Agent、不同开发阶段、CUDA 与 SCALE、不同优化级别。你关心的往往是“表面相似，实际差异在哪里”。

A 使用“编程形式上可以类比，但是设计内核完全不同”建立区分；C 则说“这里尽量和第二节的CUDA代码保持了一致，希望能够对比编译器的结果。”这表明比较不仅是语言修辞，也会体现在示例选择上。[A：21](<../corpus/derived/AMReX开发中的AI助力总结.md#L21>) [C：457](<../corpus/derived/异构编程的编译流程（笔记）.md#L457>)

B 的“代码等价 ≠ 性能等价。”则把比较后的判断压缩成一句可单独阅读的话。[B：55–61](<../corpus/derived/KubeCon China 2026 参会技术报告.md#L55-L61>)

**复用规则：**比较时说清比较维度；近似对应与完全等价分开。不要只罗列 A/B 特征，要说明差异对当前任务的影响。

### 4. 解释原因，最终回到工程影响

你不只写“有什么”，还常继续回答“为什么”“这说明什么”“下一步应该关注什么”。

- A 把能力边界继续拆成 API 状态、架构差异和编译器优化边界。[A：17–23](<../corpus/derived/AMReX开发中的AI助力总结.md#L17-L23>)
- B 用“这件事情对我们的 Agent 很重要，因为它说明：”把外部案例转成自身问题，随后落到优化规则应加入哪些分析指标。[B：55–61](<../corpus/derived/KubeCon China 2026 参会技术报告.md#L55-L61>)
- C 从汇编中的地址与读写行为，解释冗余访存，再补充调试目标和向量化条件。[C：657–689](<../corpus/derived/异构编程的编译流程（笔记）.md#L657-L689>)

**复用规则：**一段技术说明尽量完成“现象或对象—原因或机制—实际影响”的联系。不是每段都要套齐三步，但重要判断要有推导，重要建议要有来由。

### 5. 有作者在场感，但不是以个人经历为主线

A 的“我认为”、B 的“对我们的转码 Agent”、C 的“我目前仅关注两个内容”，都让读者知道判断来自哪个工作视角。[A：49](<../corpus/derived/AMReX开发中的AI助力总结.md#L49>) [B：21](<../corpus/derived/KubeCon China 2026 参会技术报告.md#L21>) [C：378](<../corpus/derived/异构编程的编译流程（笔记）.md#L378>)

这种个人声音主要用来标明关注点、经验范围和团队关联。正文大量内容仍是技术说明，因此也不宜每段都加“我认为”。

**复用规则：**涉及经验与建议时保留“我／我们”；描述机制时可以直接说明。没有材料支持时，勿替作者补写“我已经测试”“我们已经实现”等经历。

### 6. 既会直接下判断，也会交代来源与条件

你的语气不是始终保守。A 对某些开发场景的局限判断较强；B 对重要趋势会明确强调价值；C 也会用“注意”及感叹号强调观察结果。另一方面，文本又保留“目前”“可能”“如果未来”等条件。[A：17–23](<../corpus/derived/AMReX开发中的AI助力总结.md#L17-L23>) [B：29、97](<../corpus/derived/KubeCon China 2026 参会技术报告.md#L29-L97>) [C：1045](<../corpus/derived/异构编程的编译流程（笔记）.md#L1045>)

两处尤其有辨识度：

> “以上规模与效率数字均为现场展板展示口径。”[B：167](<../corpus/derived/KubeCon China 2026 参会技术报告.md#L167>)

> “如有发现不准确的地方，请及时联系我修改，以免误导。”[C：382](<../corpus/derived/异构编程的编译流程（笔记）.md#L382>)

**复用规则：**已经支持的结论直接表达；个人推断标明推断，外部数字保留来源归属，依赖特定环境的结论写清条件。不要为了模仿强语气而扩大技术断言。

### 7. 中文组织逻辑，英文保留技术精度

三篇都自然保留 Agent、Chat、kernel、memory、PTX、SASS 等表达。解释主要是中文，英文对象嵌入中文句法；必要时补一句功能或机制，而非把每个名词全部翻译一遍。

例如 B 用“瓶颈并不是计算量，而是 tensor 在 VRAM 和 SM 之间反复移动。”解释性能问题；C 用“可重定位目标文件（`.o`）”连接概念与实际文件。[B：43](<../corpus/derived/KubeCon China 2026 参会技术报告.md#L43>) [C：825](<../corpus/derived/异构编程的编译流程（笔记）.md#L825>)

**复用规则：**保留团队常用术语，优先解释它在这里做什么。面对非技术读者，再有选择地补充释义；不固定要求“每个英文词首次出现都附全称”。

## ✍️ 句式、段落与阅读节奏

### 句子不是越短越像你

A 的开篇、B 的架构解释、C 的目标文件解释，都包含较长的复合句。并列、因果、括号和转折经常共同承载技术关系。你的特点更像是**解释可以展开，关键判断要抓得住**，而非全篇短句。[A：5](<../corpus/derived/AMReX开发中的AI助力总结.md#L5>) [B：21](<../corpus/derived/KubeCon China 2026 参会技术报告.md#L21>) [C：825](<../corpus/derived/异构编程的编译流程（笔记）.md#L825>)

复用时可以保持“说明段落＋短条目或判断句”的交替。只在并列关系过密、指代不清时拆句，不设统一字数上限。

### 常见的句法骨架

以下是从样本抽象出的表达结构，不是每篇都要用的固定台词：

| 功能 | 可复用骨架 | 使用提醒 |
| --- | --- | --- |
| 定义范围 | “本文主要……”“这里先讨论……” | 交代真实范围即可 |
| 拆分问题 | “主要包括……”“可以分成……” | 分类须对后文有用 |
| 校正认识 | “不是只……而是……”“形式上……但……” | 保留实质差异 |
| 给出解释 | “因为……所以……”“这说明……” | 别省略中间依据 |
| 引入范例 | “下面以……为例”“可以看到……” | 材料要支持观察 |
| 标明判断 | “我认为……”“对我们的……有参考价值” | 避免冒充验证结果 |
| 限定场景 | “目前……”“在……条件下”“如果未来……” | 只保留必要限定 |

这些连接方式值得学习，但“不是……而是……”在 B 中尤其突出，后续生成时应适量使用，避免句句对仗。

### 排版主要承担技术功能

共同点是把层次、并列项、流程和重点显形：标题帮助导航，列表拆分内容，箭头压缩过程，行内代码区分命令与文件，强调标记提示结论或易错点。

具体形式有差异：A 有评分表，B 常用截图与独立强调句，C 大量保留代码和机器输出。因此，适合学习的是“根据材料选形式”，不是强制每篇配表、配图、配代码。A 中的星级也只代表该篇的定性评价方式，不是通用评分制度。[A：33–39](<../corpus/derived/AMReX开发中的AI助力总结.md#L33-L39>) [B：35–37](<../corpus/derived/KubeCon China 2026 参会技术报告.md#L35-L37>) [C：758–821](<../corpus/derived/异构编程的编译流程（笔记）.md#L758-L821>)

## 📚 三种文体分别怎么写

| 文体 | 当前样本的组织方式 | 后续仿写重点 |
| --- | --- | --- |
| 工作复盘 | 当前方式→按工作环节分析→归纳收益与局限→个人思考 | 保留经验视角与任务边界，说明有效和效果有限的部分 |
| 会议技术报告 | 业务相关的总览→重点案例→补充议题→核心信号 | 筛选而非罗列，区分会议材料与作者判断，把案例带回团队场景 |
| 技术学习笔记 | 学习目的→整体流程→具体示例与输出→局部解释→相关基础补充 | 保留教学路径，用对应关系和可观察产物讲明白机制 |

共同的是问题导向与解释方式，差异在信息组织。尤其要避免两种套用：

- 把会议报告写成逐个展台、逐场演讲的流水账，丢掉“与我们有什么关系”的筛选。
- 把技术笔记改成只有结论的管理摘要，删掉支撑理解的示例、命令与中间产物。

也无需强制所有文章“先给最终结论”或“结尾必须有总结”。B 的总览较强，C 则有明显的边讲边推导和待补充状态。[B：7–13](<../corpus/derived/KubeCon China 2026 参会技术报告.md#L7-L13>) [C：475–479](<../corpus/derived/异构编程的编译流程（笔记）.md#L475-L479>)

## ⚙️ 可执行的风格规则

### 优先保持

1. 从真实工作问题或明确学习目的切入。
2. 先理清对象、阶段或层次，再讨论能力与影响。
3. 对重要差异解释原因，不只贴结论标签。
4. 用具体示例、命令输出或来源材料承接抽象概念。
5. 把外部案例重新映射到自己的工作，而不是停在信息转述。
6. 保留作者必要的“我／我们”视角，尤其是经验、关注点与建议。
7. 中文承担叙述，英文保留技术对象；解释到读者能跟上即可。
8. 允许较长说明句，配合列表、局部短句和重点提示组织节奏。
9. 区分材料所说、实际观察、个人推断和行动建议。
10. 遇到真实技术限制时写清，不用空泛的积极评价替代分析。

### 随场景调整

- 会议报告可以更强调来源、数字口径和对团队的启示。
- 复盘可以增加主观感受，但感受应落在具体任务与结果上。
- 学习笔记可以展开示例和中间过程，正文优先解释关键观察点。
- 只有存在实际顺序时才画流程；只有存在比较维度时才用表格。
- 对同事无需补齐每个基础概念；对跨团队读者适当增加定义。

### 不作为风格习惯保留

- 导出带来的反斜杠转义、空引用行和加粗接缝。
- 中英空格、大小写和代码围栏语言标签的不统一。
- 示例中的本机目录、内网信息、具体人名或内部附件。
- 错别字、偶发标点与尚未完成的草稿痕迹。
- 粘贴的技能说明中的命令式语气、工具角色或模板句。

这些内容可以在排版和润色时修整，不应为了“像本人”而刻意复刻。正文中对技术对象的强判断也应随证据校准，而不是变成跨任务套用的固定观点。

## 💬 可直接复用的风格说明

下面是从本档案压缩出的写作指引，不是插件，也不包含原始工作资料。

```text
请按我的工作技术写作风格起草或润色。

读者以有一定技术基础的同事为主。先说明当前工作问题或学习目的，再组织技术内容；避免无关的宏大背景。把对象、阶段和层次拆清楚，通过对比和具体示例解释机制，回答差异为何影响实际工作。

保留必要的“我／我们”视角，表达关注点、经验范围和建议。技术说明可以展开，用列表或短判断句帮助扫描，不要机械地把所有句子改短。中文组织逻辑，英文保留常用技术术语，按读者需要解释其功能。

已有依据的判断直接表达；推测写明推测，外部数字保留来源，特定环境的结论带上条件。不要补写未提供的实验、经历、数字或内部信息。不要把示例推成普遍规律。

先区分文体：工作复盘突出任务与效果；会议报告突出筛选、证据和业务启示；学习笔记保留示例、中间产物和推导过程。排版服务于理解，不强制每篇使用同一模板或固定句式。

目标是让问题和判断讲得清楚，保留工程师与同事讨论问题的语感，而不是改成宣传稿、空泛总结或高度统一的标准报告。
```

## 🧪 风格示范与核对清单

### 示范：将泛泛评价改为带条件的工作判断

以下为新写的示范，不是原文引述，也不表示你已实施或验证相关工作。

**待改写句：**“Agent 技术具有广阔应用前景，能够全面提升研发效率。”

**按本档案组织：**

> 在讨论 Agent 能带来多少帮助之前，先把任务分开看。对于流程已经明确的环节，可以考虑让 Agent 按既定步骤执行；对于依赖目标硬件和编译器行为的部分，还需要把实际结果纳入判断。这里更值得关注的，不是一次生成了多少代码，而是修改后的结果是否经过验证、是否对当前任务有效。

这个示范保留了“任务分类—条件—评价标准”的关系，但不代表以后每段都需要这些句式。只有作者确认“像我”，它才适合成为后续参考样例。

### 成稿后检查

- [ ] 开头说明了写作目的，与实际工作或学习需要有联系。
- [ ] 分类和层次有用，不是为了凑点数。
- [ ] 核心判断能找到对应的理由、案例或观察材料。
- [ ] 相似对象之间的差异及其影响已经解释清楚。
- [ ] 作者经验、外部说法、推断和建议的归属可辨认。
- [ ] 技术术语保持准确，解释深度符合读者基础。
- [ ] 关键条件与结论的确定程度一致。
- [ ] 没有替作者添加未提供的实验、数字或工作经历。
- [ ] 解释没有被过度压缩，也没有用长篇材料代替分析。
- [ ] 阅读时像同事间的技术交流，而不是套模板的产品介绍。

## 🔄 置信度与下一轮校准

### 当前证据较强的部分

工作相关性优先、分类拆解、对比解释、中文叙述中保留英文术语，以及对适用范围的关注，均能在三篇中找到直接依据。它们适合作为工作文风的基础规则。

### 需要按文体使用的部分

业务启示的密度、数字来源的标注方式、命令输出的展开程度，以及个人感受的篇幅，都受文章目的影响。它们适合作为不同文体的分支，而不是统一硬性要求。

### 仍待作者确认的部分

1. **正式程度：**日常分享和正式对外稿之间，你希望保留多少口语与个人判断。
2. **解释长度：**代码和原始输出通常保留多少放正文，多少移到附件；现有样本差异较大。
3. **措辞偏好：**哪些词是主动选择，哪些来自素材、AI 辅助或一次性写作情境。
4. **可接受的润色幅度：**更重视保留原句语感，还是允许重新组织段落。

后续最有价值的材料，是“初稿＋你最终修改后的定稿”或你明确认可的短篇段落。它们有助于区分稳定偏好与现有文章的偶发形式。当前不设句长、加粗比例、术语密度等精确目标，也不声称已经完整复现你的个人写作风格。
